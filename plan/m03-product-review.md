# M03 product and acceptance review

Reviewer: independent product/acceptance reviewer | 2026-10-31 Asia/Shanghai
Verdict: **APPROVED after re-review** for the proposed [M03 plan](milestone-03.md). This is a planning review, not implementation or milestone acceptance.

The plan grounds reproducibility in inspectable synthetic evidence, distinguishes execution and stored identities and pre-save snapshots, and correctly avoids claims of environment recreation, hardware qualification and durable recovery. Its codec, legacy, outcome and clean-process matrices are testable once W01 chooses fields, backend and numeric tolerances. M02 closure evidence at local `e827e7f` supports the stated prerequisite; the distinct signal-monitor client currently returns an in-memory record and does not persist or expose a procedure manifest. W01 must establish the cost and supported handoff needed to use it as real persistence evidence rather than assuming an existing stored client. The W02/W03 split is plausible only if schema semantics can be tested without prematurely committing an unreviewed persistence format; product and architecture should recombine or narrow if the design cannot safely split them.

## Findings

- **PO-M03-01 — Decision branch does not fully govern later acceptance.** W01 can select separate client-specific records or reject a common schema, yet W02 unconditionally calls for an accepted smallest schema/codec for supported clients and W04 requires both clients to demonstrate the selected boundary. Explicitly define the viable downstream path for a reviewed no-common-schema decision: either amend the milestone scope and W02–W04 acceptance through Product/Architect approval or stop/replan rather than implying a common implementation still proceeds. Distinguish minimum per-client stored evidence from an unsupported shared API.
- **PO-M03-02 — Reproducibility oracle needs an explicit selection gate.** W04 says compare specified numeric tolerances and configuration, but no earlier acceptance requires choosing independent reference inputs, deterministic expected sample/timing relationships, tolerances, excluded fields and a separate-process rerun procedure for each supported client. Require W01 to inventory reproducible inputs and observability, and each later PRD/design to freeze the oracle before implementation; record when the second client lacks persisted context or a public clean-session entry point. This prevents arbitrary self-comparison or silent omission of a field from becoming an acceptance pass.
- **PO-M03-03 — Outcome-stage and persistence failure matrix needs decision-complete acceptance.** The plan correctly rejects projecting later success into a pre-save snapshot, but W03 leaves chosen snapshots/updates and writer/reader failures open-ended. Require the W01/W03 design to enumerate supported stages and unavailable reasons, whether later outcomes are intentionally absent or updated, and assert what happens on serialization failure, save failure, close/disconnect failure and malformed/unsupported reload. Specify which original bytes and independently observable primary/cleanup diagnostics must remain available, without implying atomicity or partial recovery. These are scoped matrix obligations, not a demand to persist failed runs.

## Debt and feasibility disposition

The listed generic scheduler and timeout defects, metadata constructor and HDF5 destructive-reader defects, OBS-004/005/006 and DEFECT-2 match M02 closure as read from `e827e7f:log/release_11/closure.md`; `set_meta(None)` mismatch is additionally identified by the plan. HDF5 safe-copy behavior and metadata hydration are materially relevant to the proposed path; SQLite should be characterized independently and excluded unless evidence supports it. Reserve explicit review time for actual dependency/source availability and fresh-environment work, which M02 evidence showed can be slow; do not turn a network failure into acceptance. No unreviewed storage repair, partial recovery or hardware work should be bundled into these increments.

Review findings require author revision and independent reinspection. No runtime tests, document validation, candidate CI or new product acceptance were performed for this planning review.


## Independent re-review and closure

The revised plan requires Product/Architect revision of W02–W04 and the milestone exit before proceeding without a common schema (PO-M03-01); requires W01 client input and observability inventory and later PRD/design oracles, tolerances, exclusions and separate-process rerun procedures before implementation (PO-M03-02); and requires explicit outcome stages and unavailable reasons, serialization/save/close/reload failure behavior, original-byte preservation and independently observable diagnostics (PO-M03-03). The reviewer closes all three findings. This approval is for planning only; no execution or milestone acceptance is claimed.
