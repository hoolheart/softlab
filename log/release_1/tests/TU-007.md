# TU-007 test-case gate

Owner: sw-mike. Status: **expected RED**; developer review and detailed
design approval pending. Production unchanged (tip `79c7d72`, docs-only
task-start commit). Proposed API below is a test contract for review, not
an assertion that implementation exists.

## Grounding: current theory reality (unchanged production code)

Inspection of `softlab/tu/theory/model.py` and `mapping.py` at branch tip
`79c7d72` grounds this contract (with the TU-001 matrix in
`log/release_1/compatibility.md`):

- `TheoryModel.features` wraps `calculate_features()` in a bare
  `try/except` and returns `{}` on **any** exception. The TU-001 matrix
  row "validated model attributes and legacy feature failure fallback"
  deliberately characterizes this swallow (OBS-005): it stays as the
  legacy lenient path, and TU-007 must add an opt-in strict path that
  exposes errors — the swallow itself is never certified as desirable.
- Model identity today is only `name` (empty string default) and
  `__repr__`; there is no description, no configuration surface, and
  `add_attribute(key, vals, initial_value)` carries no semantic
  description. Attributes are delegated `LimitedAttribute`s, so the
  existing `Validator` chain (`validate()` raising on failure) is the
  single validation path any configuration write must reuse.
- `Mapping` already owns all shape/type checks: argument count
  (`RuntimeError`), ndarray input type (`TypeError`), input shape
  (`ValueError`), result type/shape (`RuntimeError`), plus
  `batch_mapping` batching. PRD requires these be **retained rather
  than duplicated** — the new contract adds no second shape-check layer,
  and the guard case exercises the existing checks unchanged.
- Public imports are `Mapping`, `TheoryModel`, `batch_mapping` from
  `softlab.tu.theory` (re-exported via `softlab.tu`); the guard pins
  their identity.
- No evaluation-side I/O exists (pure computation), so inspection cases
  need only synthetic in-memory models; no hardware, no files.

## Proposed minimal surface

Additive, on `TheoryModel` only; `Mapping`, `batch_mapping`, the legacy
`features` property and public imports untouched:

- **Identity and semantic description:**
  - `TheoryModel.describe() -> Dict[str, Any]` — opt-in versioned
    semantic description (`schema_version` 1), exposing `name`, the
    model kind (class identity, JSON-safe) and per-attribute entries
    with their semantic `description`. It performs **no evaluation**: a
    model whose `calculate_features` raises is still describable.
  - `TheoryModel.add_attribute(..., description: str = '')` — optional
    semantic description keyword, default empty (existing three-argument
    calls unchanged).
- **Supported serializable configuration:**
  - `TheoryModel.supported_configuration()` — declares the supported
    serializable configuration keys explicitly; the declaration is
    independent of current attribute values and JSON-safe.
  - `TheoryModel.configuration() -> Dict[str, Any]` — reads the current
    configuration (JSON-serializable values).
  - `TheoryModel.configure(cfg: Dict[str, Any]) -> None` — applies a
    configuration. Unsupported keys are rejected explicitly: unknown
    keys raise `KeyError` naming the key with **no partial
    application**; a non-mapping argument raises `TypeError`. Values
    pass through the **existing** per-attribute `Validator` chain
    (validation reused, not duplicated), so a failed `configure` leaves
    all previous values intact.
  - Round trip: `configure` followed by `configuration` returns equal
    values, and configuration stays consistent with delegated attribute
    access (single source of truth).
- **Opt-in strict evaluation:**
  - `TheoryModel.evaluate_features(strict: bool = False)` —
    `strict=True` propagates the original exception object from
    `calculate_features` unchanged (error-cause policy consistent with
    TU-006); `strict=False` preserves the legacy lenient semantics
    (`{}` on failure). The legacy `features` property is untouched and
    keeps its characterized behavior (OBS-005 disposition: the swallow
    survives only on the legacy/lenient paths).

Designer may refine naming (`describe`, `supported_configuration`,
`configuration`/`configure`, `evaluate_features`, the `description`
keyword) through an explicit test-plan revision; the acceptance
semantics above are the contract under test. Case groups are
independent so implementation can be validated incrementally.

   features success and update through delegated writes, validator

   `get_mapping`.

   (green)**: fixed-shape ndarray mapping call, `batch_mapping`,
   metadata, and all five existing check outcomes (TypeError/ValueError/
   RuntimeError variants) — the checks the new contract must reuse, not
   re-implement.
3. `test_public_imports_unchanged` — **guard (green)**: `Mapping`,
   `TheoryModel`, `batch_mapping` identity via `softlab.tu.theory`.

Group A — identity and semantic description (RED):

4. `test_model_identity_and_semantic_description` — versioned
   description (`schema_version` 1), name, model kind present,
   per-attribute descriptions (provided text echoed, default `""`),
   empty-name model identity preserved.
5. `test_description_performs_no_evaluation` — a model whose
   `calculate_features` always raises is fully describable; description
   never evaluates.

Group B — supported serializable configuration (RED):

6. `test_supported_configuration_declared_explicitly` — declaration
   covers exactly the attribute keys, is independent of current values,
   and is JSON-safe.
7. `test_supported_configuration_round_trip` — initial configuration
   equals attribute values and dumps to JSON; `configure` then
   `configuration` returns the new values; delegated access sees the
   same values (single source of truth); re-applying the read
   configuration is an identity.
8. `test_unsupported_configuration_keys_rejected_explicitly` — unknown
   key raises `KeyError` naming the key; previous configuration fully
   intact (no partial application); non-mapping argument raises
   `TypeError`.
9. `test_existing_validators_reused_for_configuration` — out-of-range
   `configure` value raises the same `ValueError` as a delegated write
   and changes nothing (existing validator chain, not a duplicate).

Group C — opt-in strict evaluation (RED):

10. `test_strict_evaluation_exposes_original_error` —
    `evaluate_features(strict=True)` propagates the identical exception
    object raised by `calculate_features`.
11. `test_lenient_path_unchanged_beside_strict` — strict success equals
    the legacy feature dictionary; under a patched failure the legacy
    `features` property and `evaluate_features()` / `(strict=False)`
    all keep the lenient `{}` semantics while `strict=True` exposes the
    identical error object.

## Latent-defect fix at first RED run (test cases only, production unchanged)

The first run showed 10 errors instead of the designed 8: both guard
cases 1 and 2 built the fixture through `_make_model()`, which passed
the new `description=` keyword — guards must pass against unchanged
code, so the fixture now takes `with_description: bool = False`
(default) and only the identity case (4) opts in; and guard case 2
compared ndarrays with `assertEqual` (ambiguous truth `ValueError`),
now `assert_array_equal`. Fixed before recording evidence below; no
assertion was weakened and no RED case was removed.
