# TU-003 test-case gate

Owner: sw-mike. Status: expected RED; developer review and detailed design
approval pending. Production unchanged. Proposed API below is a test contract
for review, not an assertion that implementation exists.

## Proposed minimal surface

`VisaCommand.execute()` and `VisaCommand.describe_operation()`, both on the
existing `VisaCommand` class only. No universal instrument hierarchy, no new
base class and no constructor changes are proposed; the legacy read-only
`Parameter` invocation path remains untouched.

- `VisaCommand.execute() -> Any`: explicit operation path. Each call performs
  exactly one `handle.write(cmd)` and returns the stored value, matching the
  per-call side-effect semantics of legacy `get()`. It is the only invocation
  that experiment authors need to call explicitly; it never reads or writes
  beyond that single command write.
- `VisaCommand.describe_operation() -> Dict[str, Any]`: side-effect semantics
  lookup. Returns a detached JSON-compatible dict with `schema_version` 1,
  `name`, `effect` (`'write'` for VISA commands) and `executions_per_call`
  (1). It performs zero device I/O and never contains the command string or
  resource address. This is a separate lookup from the TU-002 version-1
  `describe()`, whose schema is not reinterpreted.
- Errors: denied legacy `set` keeps raising `RuntimeError` before any write.
  Transport failures from `execute()` propagate unchanged (original cause
  preserved); an unavailable resource raises the handle's `RuntimeError`.

Designer may refine this surface through an explicit test-plan revision.

## Acceptance cases (`tests/test_tu_operations.py`)

1. `execute` exists and is callable; one call writes the command once and
   returns the stored value; two calls write exactly twice.
2. `describe_operation()` is JSON, versioned, documents `effect='write'` and
   `executions_per_call=1`, hides the command string and performs zero I/O.
3. Legacy compatibility: `snapshot()` writes nothing; `command()` and
   `command.get()` each write exactly once; denied `set` raises RuntimeError
   with no additional writes.
4. `describe()` (TU-002 v1) performs zero I/O, exposes no command string,
   and a subsequent legacy call still writes exactly once.
5. Denied `set` performs no execution; `execute()` propagates a VISA
   transport error with the original cause preserved.
6. `execute()` on an unavailable resource raises the handle's RuntimeError
   after exactly one attempted write.

Cases 3 and 4 are compatibility guards that pass against unchanged legacy
code; cases 1, 2, 5 and 6 require the new API and are the RED cases.
