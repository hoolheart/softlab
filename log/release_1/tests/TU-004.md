# TU-004 test-case gate

Owner: sw-mike. Status: expected RED; developer review and detailed design
approval pending. Production unchanged. Proposed API below is a test contract

## Grounding: current lifecycle reality (unchanged production code)

Inspection of `softlab/tu/station/device.py`, `station.py`, `visa.py` and
`parameter.py` at branch tip `5782c4a` grounds this contract in reality
rather than invented requirements:

- `Device` has **no lifecycle API at all**: no `prepare`/`cleanup`/
  `initialize`/`connect`/`supports`. Construction is pure container setup
  (name, parameter/child dicts, delegation) and performs zero I/O, so a
  plain `Device` is already effectively virtual and must stay that way.
- The only connection lifecycle in `tu` is `VisaHandle`: eager
  `open_resource` + optional `clear` inside `__init__` (compatibility
  matrix row "eager open/clear"). OBS-003 records that acquisition
  precedes clear/termination setup with no explicit cleanup guard on
  failure, and resource-manager ownership is unspecified. That existing
  VISA behavior is characterized legacy, not changed here; TU-004's
  contract is the opt-in `Device` lifecycle contract proposed below,
  which TU-006 may adopt for VISA compatibly.
- `Parameter.owner` expresses device→parameter ownership, but there is
  no resource-ownership concept at the device level; the proposed
  surface adds one without touching `Parameter`.

## Proposed minimal surface

Opt-in methods on the existing `Device` base class only. No new base
class, no constructor changes, no universal instrument hierarchy;
subclasses opt in through two protected hooks. Legacy subclasses that
override nothing remain virtual devices with unchanged behavior.

- `Device.supports(capability: str) -> bool` --- explicit, side-effect-free
  capability detection. Base (virtual) device: `False` for `'connection'`
  and any unknown capability, `True` for `'prepare'` and `'cleanup'`.
  Never performs I/O and never raises for unknown names.
- `Device.prepare() -> None` --- explicit preparation. For a virtual
  device it is a no-op that acquires and opens nothing (no resource
  manager, no connection). On success it makes the device ready; a
  failure in the subclass hook propagates the original exception and
  leaves the device not initialized.
- `Device.initialized -> bool` --- explicit readiness. `False` on a fresh
  device, `True` only after successful `prepare()`, `False` again after
  `cleanup()` or failed preparation.
- `Device.cleanup() -> None` --- explicit, idempotent release of owned
  resources only. Safe before any successful preparation (a non-owner
  releases nothing, so borrowed resources are never released by a
  non-owner), safe after failed preparation (partial acquisition
  released exactly once), and repeated cleanup after success invokes the
  release path at most once.
- Protected opt-in hooks `_prepare_impl()` / `_cleanup_impl()`, both
  no-ops in the base class. Subclass implementations express the actual
  acquisition/release; the base class owns state, idempotence, readiness
  and failure semantics.

Designer may refine this surface (naming, ownership bookkeeping) through
an explicit test-plan revision; the acceptance semantics above are the
contract under test.

## Acceptance cases (`tests/test_tu_lifecycle.py`)

1. Virtual device requires no meaningless connection operation:
   `supports('connection')` is `False`; `prepare()` performs zero
   PyVISA resource-manager activity; device remains fully usable.
2. Readiness is explicit: `initialized` is `False` before `prepare()`,
   `True` after, `False` after `cleanup()`.
3. Unsupported capabilities are detectable without side effects:
   `False` for `'connection'`/`'trigger'`/`'raw-bus'`/empty, `True` for
   `'prepare'`/`'cleanup'`, zero I/O during detection.
4. Repeated cleanup is idempotent after success: release hook invoked at
   most once across two `cleanup()` calls.
5. Cleanup before any successful prepare is a safe no-op: non-owner
   releases nothing.
6. Failed preparation propagates the original exception and leaves the
   device not initialized.
7. Failed preparation followed by cleanup releases the partial
   acquisition exactly once; still idempotent on a second cleanup.
8. Borrowed resource is not released by a non-owner: a device holding an
   externally-owned resource, cleaned up without successful preparation,
   never closes the borrowed resource.
9. Legacy compatibility guard (passes against unchanged code):
   construction, parameter/child management, delegated access, ownership
   links, snapshot structure and batch setting are unchanged and perform
   no connection activity.

Cases 1–8 are the RED cases requiring the new API; case 9 is the
intended legacy-compatibility guard.
