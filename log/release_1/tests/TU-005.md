# TU-005 test-case gate

Owner: sw-mike. Status: expected RED; developer review and detailed design
approval pending. Production unchanged. Proposed API below is a test contract
for review, not an assertion that implementation exists.

## Grounding: current read reality (unchanged production code)

Inspection of `softlab/tu/station/parameter.py` and `visa.py` at branch tip
`8e898c4` grounds this contract in reality rather than invented requirements:

- `Parameter.get()` / `__call__` are strictly value-only: permission check,
  `before_get` hook, encoder, stored value — no timestamp, no quality, no
  metadata carrier. `huo` `AtomJob` consumes readings via `para()` value
  calls (`huo/process/common.py`), so the legacy value-only path is a live
  compatibility contract (TU-001 matrix row "count/scan retain numeric
  value-only behavior").
- Acquisition already exists as a hook: `VisaParameter.before_get` performs
  the actual `handle.query(...)` *during* `get()`, and `VisaCommand` performs
  its write as a `before_get` side effect. A richer read must reuse this
  same acquisition chain (so acquisition counts and error propagation stay
  identical), not invent a parallel path.
- TU-002 `describe()` schema version 1 is fixed; its design explicitly
  reserves later fields for TU-005 "in later schema versions" and the TU-003
  architecture review blessed separate versioned namespaces
  (`describe_operation()`) that "leave TU-005 free to extend either without
  reinterpreting the other". The reading description below therefore uses
  its own namespace, not a reinterpreted v1.
- Arbitrary nonserializable values are an established contract: TU-002 case
  3 asserts opaque objects stay readable and snapshot-compatible. The
  serialization limit must be explicit (an opt-in operation that can fail),
  never a restriction imposed on all stored values.
- OBS-004 (TU-005/TU-006) records that `VisaParameter`/`QuantizedParameter`
  call base `__init__` before installing hook fields, so settable
  non-`None` `init_value` can fail. Tests here construct `VisaParameter`
  with `settable=False` and no `init_value`, avoiding that defect rather
  than asserting it.

## Proposed minimal surface

Opt-in additions on the existing `Parameter` base class only, mirroring the
TU-003 pattern (no new base class, no universal measurement hierarchy;
legacy `get()`/`__call__` untouched and still value-only):

- `Parameter.read() -> Reading` — opt-in richer read, per call. Performs the
  same acquisition chain as `get()` (permission check, `before_get`, encoder)
  and returns a `Reading` result with `value` (equal to what `get()`
  returns), `acquired_at` (epoch seconds of the acquisition), and `quality`
  (`'ok'` on success). Exactly one acquisition per call, like `get()`.
- Failed acquisition: if the acquisition step raises, `read()` returns a
  `Reading` with `quality == 'failed'` and the original exception object
  preserved on `reading.error` — never silently swallowed, never wrapped.
  Legacy `get()` still propagates the identical exception object unchanged.
  Permission failures (`gettable=False`) raise `RuntimeError` exactly like
  legacy `get()`, before any acquisition.
- `Reading.uncertainty` / `Reading.calibration` — optional uncertainty and
  calibration reference exposed on the result, `None` unless the parameter
  declares them (optional constructor information, default `None`).
- `Parameter.describe_reading() -> Dict[str, Any]` — opt-in versioned
  description in its own schema namespace (`schema_version` 1, analogous to
  `describe_operation()`), never a reinterpretation of TU-002 `describe()`
  v1. Optional fields `unit`, `value_type`, `shape`, `channel`, each `None`
  when undeclared. Zero device I/O, never reads the stored value.
- Explicit serialization limit: `Reading` is not coerced to JSON; dumping a
  reading that carries a nonserializable value raises `TypeError`. Stored
  values remain unrestricted and readable via both `get()` and
  `read().value` (identical object identity).
- `ProxyParameter` forwards `read()` to its target, matching its legacy
  forwarding of `get()` (TU-001 proxy contract).

Designer may refine this surface (naming, `Reading` class location, quality
representation) through an explicit test-plan revision; the acceptance
semantics above are the contract under test.

## Acceptance cases (`tests/test_tu_measurements.py`)

1. Opt-in rich read exposes acquisition time and quality: `read()` returns
   a result whose `value` equals the `get()` result, `quality` is `'ok'`,
   and `acquired_at` is a numeric epoch timestamp bounded by the call;
   legacy `get()`/`__call__` remain value-only and return no result object.
2. Legacy compatibility guard (passes against unchanged code): value-only
   `get()`/`__call__` set/get and snapshot name are unchanged.
3. Optional reading description: `describe_reading()` is version-1 JSON in
   its own namespace; `unit`/`value_type`/`shape`/`channel` are `None` when
   undeclared and echo declared values; no value is read.
4. TU-002 guard (passes against unchanged code): `describe()` remains
   version 1 with exactly the v1 fields — not reinterpreted by the new
   reading description.
5. Optional uncertainty/calibration reference: absent on plain parameters
   (`None`), exposed on the reading when declared.
6. Arbitrary nonserializable value: identical object via `get()` and
   `read().value`, reading description still JSON, and `json.dumps` of the
   reading raises `TypeError` (explicit serialization limit, no coercion,
   no restriction on stored values).
7. Failed acquisition: mocked VISA query raising `VisaIOError` yields
   `quality == 'failed'` with the original exception object on `reading.error`
   and exactly one attempted query; legacy `get()` still raises the same
   object.
8. Single acquisition: mocked `VisaParameter.read()` performs exactly one
   `handle.query('MEAS?', None)`, returns encoded value, timestamp and
   `'ok'` quality; a subsequent legacy `get()` also performs exactly one
   query.
9. `ProxyParameter.read()` forwards to the target: same value and `'ok'`
   quality as a direct read.
10. Denied read: `gettable=False` makes `read()` raise `RuntimeError` just
    like legacy `get()`, with no acquisition.

Cases 2 and 4 are legacy-compatibility guards that pass against unchanged
code; cases 1, 3, 5–10 require the new API and are the RED cases.

## Actual red evidence

On Python 3.13.15 with writable `MPLCONFIGDIR=/tmp/softlab-mpl` and
`XDG_CACHE_HOME=/tmp/softlab-cache`, ran from repository root on branch
`codex/tu-005-measurements` (tip `8e898c4` plus test commit `08ac445`,
production unchanged):

- `.venv/bin/python -m unittest discover -s tests -p 'test_tu_measurements.py' -v`:
  **8 errors, 2 pass**. Every error is `AttributeError` for the missing
  `read` or `describe_reading` API on `Parameter`/`VisaParameter`/
  `ProxyParameter` — no other red cause. The two passing cases are the
  intended legacy-compatibility guards (cases 2 and 4).
- Same command with `-W error::SyntaxWarning`: identical 8/2 result, no
  warning escalated — zero warnings.

Existing suites on the same run, all from repository root:

- `test_tu_lifecycle.py`: **10 PASS**, no skips.
- `test_tu_operations.py`: **7 PASS**, no skips.
- `test_tu_descriptions.py`: **11 PASS**, no skips.
- `test_tu_contracts.py`: **17 PASS**, no skips.
- `test_compatibility.py`: **5 PASS**, no skips (includes VISA simulator).

New acceptance tests intentionally block full-suite green until
implementation; no CI/testing completion claimed. All resources are
mocks/synthetic (mocked `VisaHandle`; no PyVISA resource-manager patch
needed because only `handle.query` is exercised); no hardware accessed, no
new runtime dependencies. The pre-existing `parameter.py` `SyntaxWarning`
baseline defect recorded in the TU-003 gate remains unchanged production
code and did not recur. OBS-004 is avoided by construction (no settable
`init_value` on `VisaParameter`) and remains a recorded defect, not a
desired behavior.
