## Review issues

### [Critical] Issue 1: `describe_reading()` documented as echoing `uncertainty` and `calibration` — it does not

- **Location**: `docs/tu_extensions.md`, section 2, lines 33–37.
- **Description**: The doc states `describe_reading()` returns "the
  constructor-declared optional `unit`, `value_type`, `shape`,
  `channel`, `uncertainty` and `calibration` declarations, echoed
  verbatim." The live implementation
  (`softlab/tu/station/parameter.py:387-394`) returns exactly six keys —
  `schema_version`, `name`, `unit`, `value_type`, `shape`, `channel` —
  with **no `uncertainty` and no `calibration`**. This matches the
  authoritative TU-005 design's binding contract table (six rows, no
  uncertainty/calibration) and pseudocode. Probed live:
  `describe_reading()` on a parameter constructed with
  `uncertainty=0.1, calibration={'a': 1}` yields
  `{"schema_version": 1, "name": "p", "unit": "V", "value_type":
  "float", "shape": [1], "channel": "ch0"}` — the two declared fields
  are absent. (The `uncertainty`/`calibration` echo lives on the
  `Reading` object, which the doc's `read()` bullet already covers
  correctly.)
- **Impact**: A factual API claim in TU-008's primary deliverable that
  the live object does not satisfy. A user writing
  `describe_reading()['uncertainty']` from this guide gets a
  `KeyError`. This is precisely the class of drift the design's
  document rules forbid ("every documented signature/semantics
  statement must match the live object") and would FAIL item of the
  DC-2 documentation-consistency walk at the testing gate.
- **Recommendation**: Remove `uncertainty` and `calibration` from the
  `describe_reading()` sentence (the `read()` bullet's "echoed on both
  paths" statement is correct and stays). One-line edit; no other
  section touches this claim.
- **Status**: RESOLVED — fixed by `829cffd` (`docs(tu): correct
  describe_reading field list in guide`); re-reviewed and confirmed
  (see "Re-review of Issue 1" below).
